## 分析 backend/evaluation 测评结果

- 盘点：results*.json 13 份，数据集 3 套（retrieval_cases.jsonl 旧 chunk_index 格式 27 题、retrieval_cases_pilot.jsonl 14 题、retrieval_cases_pdf.jsonl 25 题、retrieval_cases_content.jsonl 实际 45 题）。README 写 content 是 30 题，实际 45 题（20 Vue + 25 年报，16 份文档）。
- 结论 1：results.json（Recall≈1.0）不可信——旧 chunk_index 标注 + 单文档 js.md，属标签泄漏；新 matcher 已拒绝旧格式，不要写进 README/简历。
- 结论 2：`app/evaluation/retrieval.py::normalize_match_text` 只去空白不处理 markdown 表格竖线 `|`，导致 table-aware 分块被系统性误判。pilot 集 PDF 题严格覆盖率 0.60，去掉 `|`/`---` 后 1.00；hybrid_rerank 召回 0.57 → 0.79（与固定分块持平）。"表格感知没提升"是错误结论。
- 结论 3：新数据集 pdf5（5 份年报 25 题，collection qa_chunks_pdf5_fixed）索引覆盖 25/25，但 hybrid_rerank 严格召回仅 0.52；12 个失败中 9 个"正确文档内选错块"、3 个判定误伤。根因是年报"主要会计数据"表格跨公司同构，chunk 内不含公司名，跨文档混淆占 top5 的 14%。
- 结论 4：rerank 性价比存疑（pdf5 hybrid 0.52 → rerank 0.52，延迟 630ms → 1366ms；pilot recursive 有一次 rerank 21.6s 异常值）。
- 建议优先级：修 matcher 并重算历史 results → chunk 头注入文档/表名/年份 → 建 16 文档全量 collection 跑 content 45 题 → query 侧实体抽取 + doc 元数据过滤 → 指标补分桶与 p95 延迟。
